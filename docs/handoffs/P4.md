## 5. Interfaces and contracts the next phase must preserve
* **Life is the existing `PlayerLife` machine** (`alive, downed, eliminated`; events `DOWN`, `REVIVE`, `BLEED_OUT`), owned by `server/src/death/system.ts` (`DeathSystem`). No second state machine. The room machine uses `TEAM_WIPE`, `REVIEW`, `RETRY`, `STAGE_CLEAR` as they were.
* **`CatchSystem` is the kill seam.** `capture()` (name kept) means "the ghost killed this player" and calls `CatchHost.kill`/`dead`. `CatchHost.canKill`, `contactTicks`, `satiatedTicks` are optional on the ghost host.
* **Numbers live in one table**: `death/tuning.ts` (`DEATH_TABLE`, `REVIVE`) and `shared/src/death.ts` (`SPECTATE`, `WIPE`). None depends on the stage (pinned at stages 1 and 1,000,000).
* **Protocol (additive):** client `spectate:follow`, `spectate:ping` (no coordinates), `room:retry`; server `death:state` (one player), `ghost:ping`, `death:review` (one player); optional `team[].life`. Every refusal message for a dead player is `You are dead. You can only watch.`
* **Hidden information:** a spectator's stage state is BLANKED, not filtered, and the layout it is sent has no doors; a review names no code, safe, clue, door or item id; a ping's position comes from the server. Keep it that way.
* **Retry seeds:** attempt 0 keeps the seed the stage always had; attempt k uses `deriveSeed(runSeed, 'stage', stage, 'retry', k)`. `StageRecord.attempt` is part of the contract.
* **The Revive Cell rule** (one on Easy and Intermediate, none on Hardcore, start room only, drawn after the gun and evidence, one hand) is enforced by `requireRevive` and `validateEscape`; the generator's draw order must stay.
* **The review's source:** the ghost log's `heard` and `inspect` events (with `player`, `tick`, `text`) and the cue stream. A change to what those carry changes the review.
* **The solver contract:** `solveStage` can lose its lead, waits for drops, recovers parts; `onFetched` is the drill's hook; `test/death/drill.ts` is how death is scripted.

## 6. Known bugs and incomplete work
* **No mid-run rejoin exists in this codebase** (`join` is refused once a run starts), so a reconnect cannot happen and was not built. Disconnect handling is tested (dead stay dead, the host hands over, the dropped players are removed at the retry or next stage).
* **No review for a stage cleared with deaths.** The review is built when the team is wiped. `death:review` is sent once (a client that missed it sees the banner only).
* **`dropRest` knows platforms, not walls or gates.** A part dropped where nobody can stand (inside the stage 2 gate wall, at the very top) can be moved across a closed gate. No reachable death position is moved at all (`STRICT 4`). Give it the doors before adding a standable spot beside a gate.
* **The Revive Cell is always in the start room**, so it is predictable.
* **`ghostKind`** (in the review's cause and the cue notes) names the ghost's type; P3F's evidence game must change that before it hides the type.
* **Statistical, honestly:** whether a hiding bot survives a lethal ghost with 2, 3 or 4 players is a property of the bot. The test is deterministic (seeded) but a sample; it asserts only classification, that stage 4 is always cleared, `reflex <= 4` and `cleared > 35%` of 126 runs. It is a regression guard on the bot, not a promise about the game. The strict claims are about the stage.
* **The hiding bot against a ghost that cannot kill** times out (`hide detour did not end`) with three or four players; `gun.solve` classifies instead of asserting a clear.
* **Cue notes** are sampled once per tick.
* **Server test time** is about 2.5 minutes.
* Two bot defects, hidden for a phase by loose thresholds, were found and fixed in the test helpers (a platform edge in `Bot.goTo`, a door crossing interrupted by the hiding reflex).
